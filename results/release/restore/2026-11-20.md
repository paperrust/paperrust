# Release-Prüfung „Sicherung/Wiederherstellung“ – 20.11.2026

**Ergebnis: bestanden.** Alle drei dokumentierten Wege stellen einen echten Bestand auf einem frischen
System vollständig wieder her: 40 von 40 Dokumenten, alle Dateien bitgleich, alle Metadaten, Rechte,
Suche, Vorschaubilder und Anmeldung. Über alle drei Wege gab es eine einzige Abweichung, und zwar beim
Export-Weg: zwei Zeitstempel. paperless-ngx 3.4.2 verhält sich hier genauso, und die Abweichung ist
bereits dokumentiert (siehe unten). Einen Fehler in PaperRust habe ich nicht gefunden.

- Image: `prrel_paperrust:bf77585`. Es ist auf dem arm64-Testgerät aus `git archive HEAD` (bf77585)
  plus dem `upstream`-Submodul gebaut, mit `docker/Dockerfile` wie am 20.11. nachts (thin LTO).
- Datenbank: eigenes PostgreSQL 17 je Instanz (`prrel_rN_db`). Volumes: `prrel_rN_pgdata/data/media/consume`.
- Rohdaten: `2026-11-20-raw/`. Darin `snap_r*.json` (Momentaufnahmen), `cmp_r1_r*.txt` (Vergleiche),
  `fill.log` sowie die Skripte `restore.py` und `restore_lib.sh`.

## 1. Ausgangsbestand (Instanz 1)

Frische Instanz mit leerer Datenbank (`PAPERRUST_ADMIN_USER=bench`). Mit `restore.py fill` habe ich
über die API Folgendes angelegt:

- **40 Dokumente** per `POST /api/documents/post_document/`:
  - 28 Text-PDFs (`docs/text/t000–t027`)
  - 8 Scan-PDFs ohne Textschicht (`docs/scan/s000–s007`, mit OCR)
  - 1 Scan mit 8 Seiten
  - 1 JPG und 1 PNG (Fotos)
  - 1 DOCX
  - Alle 40 wurden ohne Fehler eingelesen, in 45 s.
- **Ordnungsmerkmale:** 5 Tags, 4 Korrespondenten, 3 Dokumenttypen und 1 Speicherpfad
  `{{ correspondent }}/{{ title }}` (bei 8 Dokumenten, das ergibt Unterordner mit Umlauten).
  Dazu Archivnummern 1000–1039.
- **8 benutzerdefinierte Felder** der Typen monetary, string (mit Umlauten), date, integer, boolean,
  select, url und float. Zusammen sind es 242 Feldwerte.
- **40 Notizen**, mit Umlauten, `&`, `"` und `<>`. Eine davon hat Erika selbst geschrieben.
- **Benutzer und Rechte:**
  - Zweiter Benutzer `erika` in der Gruppe `Büro`, mit Modellrechten.
  - 10 Dokumente gehören Erika, die Gruppe Büro darf sie sehen.
  - Bei 10 weiteren Dokumenten hat Erika Sehen- und Ändern-Rechte, die Gruppe Büro Ändern-Rechte.
  - Erika sieht dadurch genau 20 Dokumente.
- **1 gespeicherte Ansicht** (Dashboard und Seitenleiste).
- **Ausgangszustand laut Prüfung:** `document_sanity_checker` meldet „No issues detected.“ Ein
  Vorschaubild haben alle 40 Dokumente. Eine Archivdatei haben 12, nämlich die Scans, die Fotos und
  das DOCX; die Text-PDFs bekommen keine. Die Suche liefert zum Beispiel `rechnung` = 31 Treffer,
  `zwetschgenröster` = 1.

Die Momentaufnahme `restore.py snap` hält je Dokument fest (Schlüssel ist die SHA-256 des
heruntergeladenen Originals):

- Titel und Zeitstempel
- Korrespondent, Typ, Speicherpfad, Tags und Archivnummer
- Dateinamen und MIME-Typ
- Eigentümer und Rechte (`full_perms`)
- Notizen samt Autor
- benutzerdefinierte Felder
- SHA-256 von Inhalt, Original, Archiv-Download und Vorschaubild
- Prüfsummen aus `/metadata/`

Global dazu:

- Benutzer (inklusive Gruppen und Rechte), Gruppen, Tags, Felder, gespeicherte Ansichten
- Treffer für 10 Suchwörter und das Ergebnis der Autovervollständigung
- Anmeldung als `bench` und als `erika` mit Passwort (`/api/token/`) sowie die Dokumente, die Erika sieht

## 2. Sicherung (wie in docs/user/administration.md und ransomware.md beschrieben)

```sh
# a) Exporter (ZIP)
docker exec prrel_r1_app paperrust manage document_exporter /usr/src/paperless/export --zip
#    -> export-2026-11-20.zip, 16,9 MB, 95 Dateien, Manifest mit 1154 Einträgen (u. a. 40 Dokumente,
#       242 Feldwerte, 40 Notizen, 50 Objektrechte, 542 Audit-Einträge)
# b) pg_dump + media/ + data/
docker exec prrel_r1_db pg_dump -Fc -U paperless paperless > paperless.pgdump      # 784 KB
docker run --rm -v prrel_r1_media:/m:ro -v prrel_r1_data:/d:ro -v $PWD/files:/b IMG \
    bash -c "tar -C /m -czf /b/media.tgz . && tar -C /d -czf /b/data.tgz ."
# c) PaperRust-Sicherung (verschlüsselt, Ziel /backup = lokaler Ordner)
docker exec -e PAPERRUST_BACKUP_PASSPHRASE='…' prrel_r1_app paperrust manage backup init --show-key
docker exec prrel_r1_app paperrust manage backup run
#    -> Snapshot 20261120T085128Z: 92 Dateien, 17,2 MB, DB-Dump 73,8 KB, 0,8 s
docker exec prrel_r1_app paperrust manage backup list
docker exec -e PAPERRUST_BACKUP_PASSPHRASE='…' prrel_r1_app paperrust manage backup check --snapshot latest
#    -> "all 93 object(s) present"
```

Danach habe ich **Instanz 1 vollständig zerstört**: `docker rm -f -v` beider Container und
`docker volume rm` aller vier Volumes. Kontrolle: Es gab keine `prrel_r1_*`-Volumes mehr.

Jede neue Instanz bekam einen **anderen `PAPERRUST_SECRET_KEY`**, so wie es auf einem neuen Rechner
wäre. Einen Admin-Benutzer aus der Umgebung gab es dort nicht; alle Benutzer kommen aus der Sicherung.

## 3. Wiederherstellung und Vergleich

### Weg A – Export → neue Instanz 2 (Doku: „Aus einem Export“)

```sh
# neue leere DB (prrel_r2_db), neue leere Volumes
docker run --rm … IMG manage migrate
docker run --rm … IMG manage document_importer /usr/src/paperless/export/export-2026-11-20.zip   # 1,4 s, rc=0
docker run -d … IMG            # Server starten
```

Ergebnis von `restore.py cmp snap_r1.json snap_r2.json`:

- 40/40 Dokumente, Original-SHA-256 alle gleich, Dokument-IDs gleich.
- Archiv und Vorschaubilder bitgleich.
- Tags, Korrespondenten, Typen, Speicherpfad, Archivnummern, Felder, Notizen, Eigentümer und Rechte gleich.
- Benutzer, Gruppen und gespeicherte Ansicht gleich.
- Alle 10 Suchwörter liefern dieselben Dokumente.
- Anmeldung `bench` und `erika` mit dem alten Passwort klappt; Erika sieht dieselben 20 Dokumente.
- `document_sanity_checker`: „No issues detected.“

Zwei Abweichungen, beide **wie in paperless-ngx 3.4.2**:

| Feld | vorher | nachher | Grund |
|---|---|---|---|
| `added` | `…09:50:04.071094` | `…09:50:04.071000` | Das Manifest speichert Zeitstempel auf Millisekunden gekürzt (DjangoJSONEncoder, wie upstream). |
| `modified` | Zeit der letzten Änderung | Zeit des Imports | upstream legt Dokumente per `bulk_create` mit `auto_now` an. |

Beides steht schon in `docs/contract/pl-cli.md` („Wie upstream (keine Abweichung, nur dokumentiert)“).

### Weg B – pg_dump + Dateien → neue Instanz 3 (Doku: „Aus pg_dump“)

```sh
docker exec -i prrel_r3_db pg_restore --no-owner -U paperless -d paperless < paperless.pgdump   # rc=0
docker run --rm -v prrel_r3_media:/usr/src/paperless/media -v prrel_r3_data:/usr/src/paperless/data \
    -v $PWD/files:/b:ro IMG bash -c "tar -C /usr/src/paperless/media -xzf /b/media.tgz && tar -C /usr/src/paperless/data -xzf /b/data.tgz"
docker run --rm … IMG manage migrate        # "No migrations to apply."
docker run -d … IMG
```

Ergebnis: **keine Abweichungen**, in allen geprüften Feldern einschließlich `added` und `modified`.
Sanity-Check sauber.

Fehler im Testablauf, kein Fehler in PaperRust: Beim ersten Versuch hatte ich die neuen Volumes zum
Entpacken unter `/m` und `/d` eingehängt. Dadurch gehörten sie root, und der Container-Benutzer (UID
1000) konnte nichts schreiben. Die Dateien fehlten also. Dabei zeigte sich trotzdem etwas Nützliches:

- Der Server lief weiter, und Suche und Metadaten funktionierten.
- Downloads und Vorschaubilder fehlten.
- `document_sanity_checker` meldete richtig „Found 40 document(s) with errors.“

Den Weg habe ich danach vollständig wiederholt, mit Einhängen unter den Image-Pfaden: sauber.
Für die Doku lohnt sich ein Hinweis: Beim Zurückkopieren von `media/` muss der Eigentümer stimmen
(UID 1000 bzw. `USERMAP_UID`).

### Weg C – PaperRust-Sicherung → neue Instanz 4 (Doku: ransomware.md „Wiederherstellen“)

```sh
docker run --rm … -e PAPERRUST_BACKUP_PASSPHRASE='…' IMG manage backup list
docker run --rm … -e PAPERRUST_BACKUP_PASSPHRASE='…' IMG manage backup restore --snapshot latest \
    --media /usr/src/paperless/media --database
#   -> "Restored snapshot 20261120T085128Z: 92 file(s), 17156174 bytes, database: 127 table(s).
#       All checksums verified."  (4,2 s, rc=0)
docker run -d … IMG   # Suchindex fehlt (data/ ist nicht Teil der Sicherung) -> wird beim Start angelegt
```

Ergebnis: **keine Abweichungen**, auch nicht bei `added` und `modified`. Die Suche funktionierte nach
dem automatischen Neuaufbau des Index, alle 10 Suchwörter lieferten dieselben Treffer. Sanity-Check
sauber.

Zusätzlich auf Instanz 4 geprüft:

| Prüfung | Ergebnis |
|---|---|
| Anmeldung per HTTP-Basic mit Passwort (`bench`) | 200 |
| falsches Passwort | 401 |
| Startseite | 302 (Weiterleitung zur Anmeldung) |
